# Claude Code global config

The design behind the agents and skills (phases, single owner per action, agent contracts, runtime validation, the decisions taken and the rollout stages) is in [`agent-workflow.md`](agent-workflow.md). It lives only in this repo and is not symlinked into `~/.claude`. The same goes for `.claude/docs/`, where the plans, specs and logs of this config's own features live (for example `.claude/docs/features/design-director/`). In agent and skill instructions `<docs>` stands for the project's docs root (see the hooks section); `project-docs` resolves it. The run states in `.claude/runs/` are git-ignored.

## Setup: symlinks

Create these links by hand on each machine, each pointing to the same name in this repo:

```sh
ln -s ~/dotfiles/.claude/CLAUDE.md   ~/.claude/CLAUDE.md
ln -s ~/dotfiles/.claude/settings.json ~/.claude/settings.json
ln -s ~/dotfiles/.claude/agents      ~/.claude/agents
ln -s ~/dotfiles/.claude/skills      ~/.claude/skills
ln -s ~/dotfiles/.claude/hooks       ~/.claude/hooks
ln -s ~/dotfiles/.claude/templates   ~/.claude/templates
```

`agent-workflow.md` and this `README.md` are not linked. Do not skip `hooks`: `settings.json` wires `python3 "$HOME/.claude/hooks/agent-audit.py"` on `PreToolUse`, and the hook fails when the file is absent, which breaks every Bash, Write and Edit call.

## skills/

Personal skills. Each one owns a phase of the workflow or a piece of know-how, and the global `CLAUDE.md` **Workflow** table routes phrases to them ("tenho uma ideia" -> `grill-me`, "cria a identidade visual" -> `design-director`, "podemos seguir com a implementação" -> `implement`, "corrige o bug X" -> `fix-bug`, "escreve o PR" -> `pr-description`). The skill holds the know-how, the agent executes: several are preloaded by agents through their `skills:` frontmatter. No skill is disabled in `settings.json` (`skillOverrides`).

| skill                  | purpose                                                                                 | preloaded by |
| ---------------------- | --------------------------------------------------------------------------------------- | ------------ |
| `grill-me`             | Discover: interview the user one question at a time until the decisions are clear, then hand off to `planner` | - |
| `implement`            | Execute an approved spec task by task through the agents, with preconditions, a resumable run state in `.claude/runs/` and an optional `--tdd` mode | - |
| `fix-bug`              | Fix a registered bug: reproduce, diagnose (read-only), regression test red by assertion, fix without touching it, gate, review, docs, close the entry | - |
| `tdd`                  | TDD where the user implements: settle the behavior, scaffold stubs that compile, tests red by assertion, hand off | - |
| `bug-repro`            | Reproduce a bug end to end as the user sees it: request + logs, failing command, or UI steps the user confirms | `quality-fixer` |
| `project-docs`         | The `<docs>/` tree: docs root, layouts and path resolution (features or legacy), scaffold, add entry, migrate | `planner`, `specker`, `backlog-keeper`, `docs-writer` |
| `docs`                 | Know-how of the documentation pass                                                      | `docs-writer` |
| `design-system`        | Maintenance of design tokens, hierarchy and accessibility, with `DESIGN_SYSTEM.md` as the single source; creating the direction belongs to `design-director` | `frontend-react`, `mobile-react-native`, `lua`, `design-director` |
| `dep-audit`            | Audit dependencies by real risk; never auto-upgrade                                      | `security-reviewer` |
| `pr-description`       | Deliver: draft the PR description and changelog entry from the diff and the feature's documents (text only) | - |
| `archify`              | Architecture, flow, sequence and state diagrams as standalone HTML                       | - |
| `new-project`          | Scaffold a new project's structure from `templates/`                                    | - |
| `onboard`              | Document an existing project per service, plus the root `CLAUDE.md` agent sections; Lua and Neovim projects get one `LUA.md` | - |
| `neovim-plugin`        | Neovim plugin and config know-how in Lua: layout and lazy-loading, `setup(opts)`, autocmds, `vim.uv` callbacks, minimum-version guards, `:checkhealth`, headless tests. Also usable alone on any Lua code for Neovim | `lua` |
| `lua-tui`              | UI in Lua: floating windows, scratch buffers, extmarks and theme-linked highlights inside Neovim; terminal TUIs (raw mode with guaranteed restore, alternate screen, `luv`, `SIGWINCH`, named ANSI colors). Also usable alone | `lua` |

Removed in stage F (see `agent-workflow.md`): `review` (its intent check moved into `code-reviewer`), `codebase-standards` (already `code-reviewer`'s standards phase), `scaffold` (now step 2 of `tdd` and the `scaffold` phase of the stack agents) and `code-simplify` (replaced by the built-in `/simplify`; its "wait for approval before applying" rule is in the Workflow table).

`implementer-contract` is not called by hand (`user-invocable: false`): it is the shared contract every stack agent preloads through its `skills:` frontmatter - inputs, write scope and scope requests, narrow-checks policy, runtime validation against the user's local instance, UI policy, out-of-scope reporting and the YAML report. Rules common to the stack agents change there, not in the eight agent files.

Visual direction is split in two, with no external plugin. **Creation** belongs to the `design-director` agent: for a project with no defined frontend it runs in rounds (brief if missing, two contrasting directions, the user's choice) and writes only `DESIGN_SYSTEM.md` (palette with light and dark, type, `Layout concept`, principles). It is never automatic: it is called only after the user's yes, from three entry points - the `new-project` question (UI services only), the Workflow phrases ("cria a identidade visual", "define o design do zero", "vamos criar o frontend do zero") and the offer in step 1 of `design-system`. **Maintenance** stays with the `design-system` skill, which keeps the file consistent afterward (tokens, hierarchy, accessibility); after creation only the main session writes the file, and stack agents propose values through `scope_requests`. Tokens already in code without a `DESIGN_SYSTEM.md` are documented by the main session following `design-system` (extraction), not by the agent. Taking the tokens to the code is a normal plan and spec.

## agents/

Global subagents, symlinked as `~/.claude/agents -> ~/dotfiles/.claude/agents` (link listed in [Setup: symlinks](#setup-symlinks)). Claude delegates to them automatically when the description matches ("Use proactively when..."), or call one with `@name`.

Each agent pins its own `model` and `effort` to balance quality and token cost:

- `opus` only where a mistake is expensive and runs are rare (reviews, planning).
- `sonnet` for implementation and fixing, the long tool-call loops where most tokens go.
- `haiku` for mechanical work whose value is a short summary, so raw logs never reach the main context.

| --------------------- | ------ | ------ | ---------------------- | ---------------------------------------------- | ----------------------------------------- |
| `code-reviewer`       | opus   | medium | read-only              | -                                              | after significant changes                 |
| `security-reviewer`   | opus   | medium | read-only              | `dep-audit`                                    | only auth, API, input, secrets, deps      |

Token-economy rules every agent follows - keep them when adding a new one:

- Model aliases (`opus`/`sonnet`/`haiku`), not full IDs, so agents follow new model versions.
- Preload only small, always-relevant skills: preloaded `SKILL.md` content is paid on every run. Larger or situational skills (`react-view-transitions`, `react-native-expo`, `react-native-performance`, `react-native-testing`, ...) are named in the prompt and loaded on demand.
- Minimal `tools` on read-only agents; no MCP servers unless needed.
- The prompt ends with a fixed YAML report. That report is all that returns to the main context, and it is the interface an external orchestrator parses.
- Expensive (`opus`) agents get narrow auto-invocation triggers or are manual only.
- Narrow checks only: agents run the tests and files they touched. Whole suites run only through `test-runner` (one gate per task, one full gate per run), honoring the project's `## Test suites` table when it has one.
- No visual validation: agents never open a browser, simulator or screenshot unless the user explicitly asks; UI work reports `manual_checks` for the user. Backend runtime validation is one request to the user's running local instance plus a filtered log read, never starting, stopping or restarting services (see `implementer-contract`).

Scope rule every agent that edits code follows - keep it when adding a new one: fix only the lint, typecheck and test problems the current change caused, or that the task names. Pre-existing problems found along the way are not fixed and not written by the agent: they go to `out_of_scope_issues` in its report, and the main session (or `/implement`, at the end of a run) hands them to `backlog-keeper` in one call, which logs them once - failing/flaky tests, type/build errors and visual defects as bugs in `<docs>/backlog/bugs/`, lint violations and code smells as refactors in `<docs>/backlog/refactor/`, one entry per root cause, deduplicated against the folder's Index. A single writer avoids duplicate entries when agents run in parallel. Likewise, agents never edit docs: they list `needs_docs`, and the documentation pass happens once, at the end.

Write-scope rule: an agent writes only inside its task's `allowed_paths`. Anything else it needs is a `scope_requests` entry with the reason; the caller asks the user and resumes the same agent with the answer.

One writer per document: `planner` writes the feature's `plan.md` (product side only), `specker` writes its `spec.md` (technical side, with an **Implementation order** of structured task blocks - Stack, Files, Depends on, Done when, Status - so `/implement` can execute them without interpreting prose; also specs for refactor entries, with no plan), `/implement` writes `log.md`, and `backlog-keeper` writes `<docs>/backlog/`. Asking `specker` for the spec of a `Draft` plan marks the plan `Approved`. Paths come from the `project-docs` skill: `<docs>/features/<slug>/` by default, or `<docs>/plans/` + `<docs>/specs/` in a project still on the legacy layout.

Subagents cannot ask the user. `planner`, `specker` and `backlog-keeper` return `result: needs_input` with the question (a missing decision, the one-time docs migration offer, a bug with no way to reproduce it); stack agents return `result: blocked` with `scope_requests`. The main session asks, then resumes the same agent with `SendMessage`.

The global `CLAUDE.md` has a **Workflow** table that routes phrases to phases ("vamos planejar" -> `planner`, "pode especificar" -> `specker`, "podemos seguir com a implementação" -> `implement`, "encontrei um bug" -> `backlog-keeper`), each with its precondition, so nothing depends on remembering to call an agent by name.

### Feature workflow

1. "vamos planejar <feature>" (or `@planner`) - review `<docs>/features/<slug>/plan.md`, answer its open questions, ask for changes.
2. "pode especificar" (or `@specker`) - review `<docs>/features/<slug>/spec.md`.
3. "podemos seguir com a implementação" (or `/implement <docs>/features/<slug>/ [tasks 2-4] [--step]`) - checks that plan and spec are approved (a Draft spec reached by a phrase needs a yes), keeps a resumable run state in `.claude/runs/<slug>.json` (tasks, budgets, approved scope, agent calls), and orchestrates: per task, stack agent (with the task's **Files** as `allowed_paths`; scope requests go to the user) -> `test-runner` -> `quality-fixer` (max 2 rounds) -> `test-writer` if tests are missing, setting the task's `Status: done` in the spec and appending its block to `log.md`, so a run can resume and the next task inherits the decisions; then one review pass (`code-reviewer`, plus `security-reviewer` for auth/API/input/secrets/deps), fixes, one full gate, `docs-writer` once with the consolidated `needs_docs`, the out-of-scope issues handed to `backlog-keeper` once, and spec and plan status `Implemented`. `--step` pauses after each task. The final report lists the docs updated and ends with the "Para validar localmente" checklist.
4. Validate locally with the checklist. For a visual check, ask for it explicitly ("tira um print de /orders"): `ui-verifier` does it and only text comes back.

### Bug workflow

1. "encontrei um bug ..." - `backlog-keeper` registers it (deduplicated, from the template) and the session asks "quer corrigir agora?" ("só registra" skips the question).
2. "corrige o bug X" (or yes to the question) - `fix-bug` runs: reproduce as the user sees it (request + logs on the local instance, the failing command, or UI steps the user confirms), diagnose with the owning stack agent in read-only `diagnose` phase, `test-writer` writes a regression test that must fail by assertion, the stack agent fixes it in `fix` phase without touching the test, `test-runner` gate, review, the repro repeated, `docs-writer` if needed, and `backlog-keeper` closes the entry with root cause and fix. Resumable through `.claude/runs/bug-<slug>.json`.

Subagents cannot spawn subagents, so chains like `test-runner` -> `quality-fixer` -> `code-reviewer` are orchestrated by the main session (that is what `/implement` encodes). The write scopes of `planner`, `specker` (`<docs>/`) and `backlog-keeper` (`<docs>/backlog/`) are enforced by their prompts, not by `tools`.

### Permissions

`settings.json` allows reading and editing `~/.claude` and `~/dotfiles/.claude` without prompts, except the `settings*.json` files themselves, which always ask (an `ask` rule): otherwise an agent could rewrite its own permissions or hooks without the user seeing it. It also allows the `Read`, `Grep` and `Glob` tools everywhere, and read-only shell and git commands (listing, search and inspection such as `ls`, `cat`, `rg`, `fd`, `jq`, `diff`; `git status|log|diff|show|blame|rev-parse|ls-files`, bare `git branch` and `git remote -v`). `find`, `printenv` and `git branch <args>` are left out on purpose: `find` can run or delete (`-exec`, `-delete`), `printenv` exposes secrets and `git branch <args>` can delete branches (`-D`), and the read-only Docker commands agents use for runtime validation (`docker compose ps|logs|port|config|images`, `docker ps|logs|inspect|port|images`), and denies the lifecycle and exec commands (`up`, `down`, `start`, `stop`, `restart`, `rm`, `kill`, `pull`, `create`, `run`, `exec`, compose or plain). Image builds are in neither list: agents run them only when the task changes a Dockerfile or its build context. Permission rules match by command prefix, so a form like `docker compose -f other.yml up` is not caught by them; the `PreToolUse` enforcement of `hooks/agent-audit.py` normalizes those forms and blocks them.

## hooks/

Symlinked as `~/.claude/hooks -> ~/dotfiles/.claude/hooks` (link listed in [Setup: symlinks](#setup-symlinks); without it every Bash/Write/Edit call fails).

- `agent-audit.py` - audit and enforcement hook. **Recording**: wired on `PostToolUse`/`PostToolUseFailure` (Bash, file writes, MCP tools) and `SubagentStart`/`SubagentStop`, async, it appends one JSON line per event to `~/.claude/metrics/<session_id>.jsonl` (outside the repo). It classifies Bash commands (narrow/package/full/load tests, lint, typecheck, docker read/build/lifecycle, git commit/push, local/external requests), checks file writes against the active run's `allowed_paths` and `approved_scope` (`.claude/runs/<slug>.json` in the project). A scoped actor's write is in scope if it matches the `allowed_paths` or approved `approved_scope` of any task in the run's `running_tasks` (tasks with agents running now, set before a parallel batch) or of `current_task`; a stale `running_tasks` only widens the scope. The record's `task` is those keys joined with `,` (bug runs stay scalar), and flags what the workflow forbids: writes outside scope, `.md` files outside the project's docs root, docs (including READMEs and `.env.example`) or backlog edited by the wrong agent, any write by a read-only agent (`ui-verifier`, `test-runner`, reviewers), browser/screenshot tools used by anyone but `ui-verifier`, suites run by agents other than `test-runner`, docker lifecycle commands, commits and pushes, external requests. Reads and searches are not recorded; neither are file contents or command output. **Enforcement**: wired synchronously on `PreToolUse` (Bash, file writes, and only the browser/screenshot MCP tools, about 50 ms per call), it applies each flagged category's action from `agent-audit.json`: `block` denies the call with the reason and what to do instead (a scope request for subagents, asking the user for the main session, `manual_checks` for docker), `ask` makes Claude Code prompt the user, `warn` lets it through with a reminder in the agent's context, `audit` only records. Blocks and asks are recorded too. It fails open: any error lets the action through. **Parsing**: a Bash command is read by a real zsh/bash parser into a tree, never split by regex; command positions, heredoc bodies and code strings come from the tree (see "Shell parser and classifier" below). A script written to a file and run later is out of its reach (see `agent-workflow.md`, 13.6). Tests: see the `tests/` entry below.
- `agent-audit.json` - the mode (`enforce` now; `audit` = record only, `off`) and the action per category. Current policy: `block` for docker lifecycle commands (also catching `-f` and `rtk` forms the permission rules miss), writes by read-only agents and browser/screenshot tools outside `ui-verifier`; `ask` for `git commit`/`git push`; `warn` for writes outside scope, suites outside `test-runner`, `.md` outside the docs roots, docs or backlog by the wrong agent, `design_system_write_by_other` and external requests; `audit` for docker builds. A `warn` category moves to `block` only after the metrics show no false positives.
  - `design_director_write_outside` (`block`): any write by `design-director` to a file that is not a `DESIGN_SYSTEM.md`, at any path (actor-only flags do not depend on a git root). `design_system_write_by_other` (`warn`): a `DESIGN_SYSTEM.md` written by anyone but `design-director` or the main session; the reminder says to propose the value in `scope_requests`.
  - Lua commands (the `lua` agent is an implementer like the other stack agents): `busted` and `luarocks test` are tests (a single `.lua` spec or test file, or `--filter`/`-t` on busted, is narrow), `nvim --headless` running plenary or mini.test (including `-c` forms) is a test, mise tasks (`mise run|r|tasks run|<task>`, `:::` chains, global flags before the task) are classified by the task name (`test*` is a test, narrow only with a file or filter argument; `lint*`, `format*` and `fmt*` are lint; `all`, `check` and `ci` are a full test run; anything else is `other`), and `luacheck`, `selene`, `stylua` and `treefmt` are lint. So a whole suite run by `lua` is `suite_by_non_runner` and a single spec file is not. `busted`, `luacheck`, `selene`, `stylua` and `nvim` also count when called by path (`./.luarocks/bin/busted`). Shell escapes inside `nvim -c`/`--cmd`/`+` (`!`, `:!`, `silent !`, `w !`, `r !`) are classified as the command they run, up to 3 levels of nesting (deeper fails closed: `unclassified_command`, reason `nested_shell_depth`).
  - Prefix stripping, for every stack: `timeout [options] <duration>` (any GNU form) and `mise exec|x [flags] --` are read as extra command positions (`command_readings`, which replaced `strip_prefixes`) before classifying, so `timeout 5 git push` is `git-push` and `timeout 60 pytest` is a full test run. A `timeout` the parser cannot read fails closed: the real command is still classified.
  - Two block categories guard the classifier itself, both denied for every actor: `command_too_long` (a Bash command over 16384 characters is never analyzed or run; write large content with the Write tool and keep commands short) and `analysis_timeout` (a 7 s wall-clock guard denies a call too complex to analyze in time; simplify or split it). The decision is printed before the metrics record is written, so a slow record loses only the record. `AGENT_AUDIT_ANALYSIS_TIMEOUT` (seconds) is a test-only override that can only lower the 7 s limit; a heredoc with more than 32 openers (`MAX_HEREDOC_OPENERS`) is classified as commands, not as data.
  - Write targets outside the repo: the governing root is the git root of the session cwd (where the run lives), falling back to the target's own root. A target inside a nested repo (submodule) of that root is judged by both roots and the flags are unioned (stricter wins). The path has `~` expanded and is resolved; with `..`, the resolved and the lexical form are both judged. A target outside every root is recorded with `area: "outside"` and its absolute path as `rel`. Actor-only flags (`write_by_readonly_agent`, `design_director_write_outside`, `design_system_write_by_other`, the last by raw or resolved name) apply to any path; area flags (`md_outside_docs`, `docs_write_by_implementer`, `backlog_write_by_other`) only inside a repo. Fixed-scope actors (implementers, `quality-fixer`, `test-writer`) in a run get `out_of_scope_write` for an outside target unless an approved `approved_scope` entry is an absolute glob matching it (literally after `~` expansion, symlinks not resolved, so a write through a symlink alias is flagged; relative globs and the always-allowed repo conventions never cover outside paths) or the path is strictly inside the session scratchpad, the `scratchpad_dir` of the hook payload (compared by path component and as given, never resolved; other sessions' scratchpads and other `claude-*` directories are not exempt). Without a usable `scratchpad_dir` there is no scratch exemption. Each outside write record carries `scratch`: `match`, `no-match` or `unavailable` (no scratchpad known). `agent-metrics.py` reports them in one line, `outside the repo during a run: N (session scratchpad: a; approved glob: g; out of scope: o; no scratchpad known: c)`. A path that cannot be resolved fails closed: actor flags, plus `out_of_scope_write` for scoped actors in a run.
  - The `DESIGN_SYSTEM.md` rule is by name, case-insensitive, in any directory (so `apps/web/DESIGN_SYSTEM.md` and `templates/**` are covered). `design-director` is exempt from `md_outside_docs` only for that name. Targets of `approved_scope` matching it are not added to the derived allowed paths, so approving a request never lets the agent write the file.
  - `md_outside_docs` (`warn`) fires only for agents; the main session and `docs-writer` never get it (their other flags stay). It needs a **new** `.md` (extension checked ignoring case) created inside the repo and outside the docs root. Newness comes from `tool_response.type` at Post, or from the target not existing yet at Pre; when unknown, the file counts as new, and a failed write (`PostToolUseFailure`) never counts. Exempt: `README.md`, `CHANGELOG.md`, `DEPLOY.md` and `CLAUDE.md` by exact file name in any case, and, during a run, `.md` paths or globs ending in `.md` in the task's `allowed_paths` or approved scope (a broad glob such as `services/api/**` does not exempt). `docs_write_by_implementer` matches the `DOC_FILES` names (`README.md`, `CHANGELOG.md`, `.env.example`, `DEPLOY.md`) regardless of case.
  - docs root: not a key of `agent-audit.json` (the old `docs_roots` list is gone). Each project declares it once as `- docs root: <path>/` in the `## Workflow` section of the root `CLAUDE.md` (the git root's, never `.claude/CLAUDE.md`), relative to the git root; this repo declares `.claude/docs/`. Without the line the root is `docs/`. The hook reads it per git root (a nested repo uses its own), only from a regular file, and never blocks on it: `.md` files under the root are not `md_outside_docs`, and `<root>backlog/` is written only by `backlog-keeper`. The value is normalized (trimmed, backticks dropped, `\` to `/`, empty and `.` segments dropped, one trailing `/`); an empty, absolute, `..` or control-character value is invalid and the hook falls back to `docs/`, while the skills stop and ask. The match is by prefix: `services/x/docs/` is not a root. `project-docs` (**Docs root**) resolves the same line for skills and agents.
  - Bounded I/O: every file the hook reads or writes goes through `_read_bounded` or `_append_line` (regular files only, `O_NOFOLLOW`, no FIFO or device blocking, size caps `MAX_CONFIG_BYTES` 64 KiB for the config and `MAX_RUN_STATE_BYTES` 256 KiB per run state, at most `MAX_RUN_ENTRIES` 256 entries of `.claude/runs/` scanned and `MAX_RUN_READS` 16 read). The metrics dir is created with mode `0700`, and a record is always appended, even when tagging the run is slow (then `in_run: false`, `run_tags: "timeout"`). A planted symlink at `~/.claude/metrics/<session>.jsonl` does not redirect the write. `tests/test_bounded_io.py` (BIO9) fails on any new open/read/write call outside those two helpers.
  - Two-level uncertainty (fail closed): when the parser cannot be sure what a command is, it never silently picks the lenient reading, and there is no tolerant reading of text that does not parse. **Level A**: every reading of the command is classified and the strictest wins; the audit flag `parse_uncertain` (`audit`, no denial by itself) and the reason in the record's `uncertainty` list are set. **Level B**: the command cannot be read or resolved, so it is denied for every actor with the block category `unclassified_command` (the message says to simplify or split the command). Reasons:
    - level A: `prefix_readings` (one token list has more than one distinct reading: stacked `timeout`/`mise exec`, or a wrapper with a flag the table does not know, which is read with and without a value), `heredoc_unclean_prefix` (a heredoc body was kept as commands because the text before the sink is not clean), `dynamic_command` (the program name comes from an expansion with no known value, and the only unknown part is a `$(...)` or backquote; recorded together with the `deny_token_unmatched` canary), `git_root_unknown` (the git root of a write target could not be determined: timeout, error or empty output; a scoped actor gets `out_of_scope_write`, everyone else only records the reason). `shlex_fallback` and `loose_assignment_truncated` no longer occur (the parser replaced `shlex`); `agent-metrics.py` still lists them for old records;
    - level B (`unclassified_command`): `lex_error` (text that does not close or is outside the grammar subset, in the command, in a code string or in a heredoc body read as shell), `nesting_depth` (more than `MAX_NESTING` = 32 nested constructs), `analysis_budget` (the characters read, the texts analyzed or the value combinations passed the budget, or more than `MAX_CODE_ARGS` code arguments in one command), `dynamic_code` (shell code the hook cannot see: code string from an unknown variable, `eval`/`source` of an expansion, a word that evaluates its own text, SQL client escapes, an unresolved forwarding call, a dynamic word in the git or docker verb region, an undecodable `$'...'` head, ...), `piped_shell` (a shell reading stdin as a non-first pipeline stage: `curl x | bash`), `nvim_shell_exec` (an nvim shell function with a non-literal command), `readings_cap` (more than `MAX_READINGS` = 8 distinct command starts in one piece, or more than `MAX_DOCKER_FORMS` = 8 readings of docker options), `nested_shell_depth` (code text deeper than `MAX_CODE_DEPTH` = 3 levels), `classifier_error` (the classifier or the parser failed to load or raised; the record gets `error: <exception class name>`, never the message), `analysis_crash` (the watchdog child died or sent an invalid, oversized or wrong-shape message);
    - canary: `deny_token_unmatched` (`audit` only): a container or git token outside command position (also path-prefixed, decoded `$'...'` and `xargs`/`parallel`/`find -exec` operands) followed by a lifecycle, push or commit verb with no matching flag. It never denies; it lists the next form that escapes the parser (see the metrics section).
  - Record fields added: `uncertainty` (list of reasons), `error` (exception class name) and `run_tags` (`"timeout"` when run tagging missed its deadline). Only `cmd[:300]` is recorded, as before.
  - Fork watchdog: the analysis of Bash, file writes and browser/screenshot tools runs in a forked child with a hard deadline (the 7 s `analysis_timeout`); the parent only decides, prints and records, so a hang or crash in the classifier cannot hang or crash the decision. The child talks to the parent over a `socketpair` with two newline-terminated JSON lines, each capped at 1 MiB: line 1 is `{"analysis": ...}` or `{"error": "<class>"}`, line 2 is `{"tags": ...}` (the run tags; skipped when the analysis already carries `in_run`). On `PreToolUse` the child waits for a one-byte go from the parent before tagging, so a call that is denied wastes no tagging and leaves no orphaned `git` process. The child leads its own process group (`setpgid`) and the parent ends it with `killpg(SIGKILL)`, which also reaches `git` grandchildren; a child still alive 1.0 s (`CHILD_GRACE_S`) after the limit kills its own group by a self-destruct `SIGALRM` (only if it leads the group, else it exits alone). No line 1 by the deadline: `analysis_timeout`; EOF or a bad line 1: `unclassified_command`, reason `analysis_crash`; a dead or late line 2: the record is written with `in_run: false`, `run_tags: "timeout"`. If `socketpair` or `fork` fails (or in `mode: off`, `mode: audit` on `PreToolUse`, other tools), it falls back to the in-process `SIGALRM` guard. The child never prints or writes metrics.
  - Fast exit: `__main__` flushes stdout and ends with `os._exit(0)`, skipping interpreter teardown (the copy-on-write teardown after a fork cost about 6 ms; with the fast exit the hook is a few ms faster than before the watchdog). Metrics are appended through raw fds, so nothing is lost.
  - Heredoc clean prefix: a heredoc body is data only for a known sink whose prefix is clean. The text before the sink head must have a single reading, no shlex fallback and no `$` expansion for `git`/`gh` heads (for `cat`/`tee`, `$` is allowed after the head, so `cat > $SP/x.sh <<EOF` is still a sink); the outer text of `$(cat <<EOF)` must have no `$` at all. Otherwise the body is kept and classified as commands (`sh -s $(true) cat <<EOF`, `A=$B cat <<EOF`, `git $X commit -F - <<EOF`).
  - Assignment prefixes: `NAME=value`, `NAME+=value` and `NAME=(...)` before a command are parsed as assignments, whatever the value holds (quotes with spaces or separators, `$(...)`, `$((...))`, `${X:-a b}`, backticks), so `A="x y z w v" docker restart api # "` is a `docker restart`.
  - Shell parser and classifier (feature `audit-shell-lexer`): the hook is three files in `hooks/`. `agent-audit.py` keeps the config, run state, metrics, decision and the fork watchdog; `agent_audit_shell.py` is the parser (pure: only `import re`, no file or process access, no mutable module state; the tree nodes are plain `__slots__` classes); `agent_audit_classify.py` is the classifier over the tree (imports only `re`, `functools`, `collections` and the parser; it owns the `MAX_*` limits and the test, lint, docker and URL patterns). Neither module imports `typing` (import cost; `tests/test_bounded_io.py` BIO11/BIO12 check the invariants). The hook loads both by path (`_load_module`: parser first, then classifier) before the fork, from checked-hash bytecode (PEP 552): the `.pyc` in `__pycache__` is used only when its header carries the hash of the source just read, otherwise the source is compiled and a checked-hash `.pyc` is written atomically (write errors ignored, `-B` honored, old timestamp `.pyc` files rejected and rewritten), so a same-size edit in the same second never serves stale bytecode. A planted `.pyc` that carries the right hash of the current source is trusted (PEP 552 checks staleness, not integrity; see the self-protection bug in the backlog). A module that is missing, has a syntax error, raises at import (including `SystemExit` and `KeyboardInterrupt`) or a classifier without its parser makes every Bash command `unclassified_command` with reason `classifier_error`; file writes and the visual tools do not depend on the classifier and keep working. Because `~/.claude/hooks` is the live code, a half-written edit of these files denies Bash calls until it is complete: write them with Write/Edit, not through Bash.
  - Grammar subset: the zsh/bash subset of the spec, section 2. Lists (`;`, `&`, newline, `&&`, `||`), pipelines (`|`, `|&`, leading `time`, `!`), simple commands with assignments and redirections (fd numbers, named fds, here-strings, heredocs `<<` and `<<-`), compounds (`( )`, `{ }`, `if`, `while`/`until`, `for`, `for ((`, `select`, `case`, `(( ))`, `[[ ]]`), function definitions, `coproc`; words with quotes, `$'...'` (decoded like bash), `$name`, `${...}`, `$(...)`, backticks, `$((...))`, `$[...]`, `<(...)`/`>(...)` and the zsh forms `$=X`, `$~X`, `$^X`. The contents of arithmetic, `[[ ]]` conditions and `${...}` are opaque: only the substitutions inside them are read as scripts. Outside the subset is level B `lex_error`: an unclosed quote, substitution, expansion, compound or heredoc delimiter, NUL, `foreach`/`always`, `repeat N {`, `&!`/`&|`, `time` or `!` after a pipe, extglob and glob qualifiers, `{ cmd }` without `;`, a `$((` that does not close as arithmetic. Not analyzed: aliases and functions of the user's shell snapshot, code in files (`bash script.sh`, `make`, `npm run`) and remote code (`ssh host cmd`, `docker exec`).
  - Heredocs and here-strings, by receiver: the body is read with bash semantics (`<<-` strips tabs, a quoted delimiter turns expansions off, a body without terminator runs to the end). A body with an unquoted delimiter always has its expansions (`$(...)`, backticks, `${...}`) analyzed as commands, whoever receives it (HD2). Data (body removed): `cat`/`tee` at top level outside a pipeline, and `cat`/`tee` with its own output redirect (`>`, `>>`, `>|`, `&>`, `&>>`) as the single stage of a whole pipeline inside a function body or `{ }` group; `git commit -F -`/`--file -` (`commit` counts only as the subcommand after the global options, so `git config --get commit.gpgsign` is not a commit; `-c alias.*` and `-c core.*` disqualify); `gh pr|issue|release ... --body-file -`/`-F -`; `$(cat <<EOF)` alone as the value of `git commit -m`/`--message` (also `--message="$(...)"`) or of `--body`/`-b`/`--title`/`-t` of those `gh` commands; `NAME=$(cat <<'EOF' ...)` (data, and the value of `NAME`). Not shell (HD4): a body for `python`, `python3`, `node`, `ruby`, `perl`, `lua`, `luajit`, `php` (and `uv|poetry|pdm|hatch|pipenv|rye|conda|mamba|micromamba|pixi run` resolved to them), only when every reading of the receiver is foreign; and for SQL and DSL clients `sqlite3`, `psql`, `mysql`, `mariadb`, `cypher-shell`, where the escapes that run programs are level B `dynamic_code` (`.shell`, `.system`, `.once |`, `\!`, `\g |`, `\o |`, `\copy program`, `\e`, `\setenv`, backquote meta-commands, `COPY ... PROGRAM`, `system`, `pager`, any `edit` word, `.sys*`/`.she*` dot-command prefixes; also inside `-c`/`-e` arguments). Any other receiver, and any heredoc on a compound (`{ bash; } <<EOF`, `while read l; ...; done <<EOF`), is a shell script analyzed one level down, and a `lex_error` in it is level B. Whole-script disqualifiers turn every body into code: a command `mkfifo`, `coproc`, `exec` with only redirections, a function named `cat`/`tee`/`git`/`gh`, a redirect to fd >= 3. Here-strings follow the same receiver rules, plus a data-reader list (`jq`, `yq`, `grep`, `sed`, `awk`, `read`, ...; `sed -f -`/`awk -f -` still read code); `bash <<< 'x'` classifies `x`; a here-string on a compound is code only when a code reader is inside.
  - Wrappers and code arguments: the wrapper table (`_WRAPPERS`, each with its own flag grammar) reaches the real command through `timeout`, `sudo` (`-u`, `-E`, `--`, `-s`, `-i`), `env` (assignments, `-u`, `-i`, `-S`), `nice`, `nohup`, `xargs`, `watch`, `time`, `stdbuf`, `ionice`, `command`, `exec`, `builtin`, `repeat N`, `mise exec`, the flagless prefixes `noglob`, `nocorrect`, `-`, `rtk`, `proxy`, and the `run` launchers above. `sudo -l/-e/-v`, `command -v/-V` and `ionice -p/-P/-u` run no command. Not wrappers (left to metrics): `doas`, `setsid`, `flock`, `chrt`, `taskset`, `find -exec`, `parallel`; the canary still records docker or git behind them. A path-prefixed program (`/usr/bin/docker`, `./bin/docker`, `~/.local/bin/mise`) and zsh `=docker` classify as the program. Code arguments are classified one level down and their categories and flags united: `bash|sh|zsh|dash|ksh|mksh|ash -c`, `eval`, `trap`, `source`/`.` of a string, `su -c`, `env -S`, `sudo -s/-i`, `watch`, `mise exec -c`, `emulate -c`, `mapfile -C`, `xargs ... sh -c`, a shell with a here-string, and the nvim shell escapes; a shell with `-n` and no `-c` runs nothing; at most `MAX_CODE_ARGS` = 16 per command. A code string made by an expansion the hook cannot resolve is `dynamic_code`; `xargs -I R ... sh -c R` and `bash < <(x)` too. A word that evaluates its own text is `dynamic_code` (zsh `(e)`/`(%)` flags, `@P`, `PS4` when tracing is enabled).
  - Value propagation: values assigned in the same text resolve the program name, the fill of a code string and a heredoc receiver (`T="docker compose"; zsh -c "$T down"`). Only the primary command start is resolved, and only for a word that is exactly `$N`, `${N}` or `"$N"` (never wrapper operands); a value is split at blanks (the most restrictive reading, even when quoted); at most `MAX_VALUE_CANDIDATES` = 16 combinations. A use before the first unconditional top-level assignment adds the environment as a candidate, is level B, and the known values are still classified (`&&` chains hold, `||` does not, so `cd x && BIN=$(...); $BIN` stays level B). A name whose whole value is one command substitution is soft: its head at the top of the text is level A `dynamic_command` (and its other known values are still classified); a mixed value, a `for` list over `$(...)`, an array element from a substitution, or a soft name inside a code string, heredoc body or the git/docker verb region is level B. Opaque texts: a text with `eval`, `source` or `.`, or a head that may hold an assigning builtin, knows no values; `+=`, `read`, `mapfile`, `getopts`, `printf -v`, `unset`, `set -A`, `declare -n` and `${N:=v}` make a name unknown; an `IFS` assignment, `setopt shwordsplit`, `set -o shwordsplit` and `emulate sh|ksh|bash` make split heads level B; zsh arrays give each element and the joined form. Heads: an unquoted brace list (`{docker,restart,x}`, up to 16 words) and the words of the parameter operators `-`, `:-`, `+`, `:+`, `=`, `:=` and `/pat/rep` are head candidates; an unresolvable brace head or any other parameter operator is level B. Quoted text with `$(` or a backquote assigned to a name (also through other names, `read` and namerefs) is tainted and is level B only when it reaches a context that evaluates arithmetic (array subscript, `(( ))`, `$(( ))`, `$[ ]`, `let`, `declare -i`, a numeric test, `${!x}`, `[[ -v`, zsh `(P)`), so sed, awk and grep patterns are not denied.
  - Git and docker forms: the verb region of `git`/`docker` runs from the program to the first literal non-option word (value options skipped, `compose` continues it); values are substituted there, and a dynamic word left in it is level B (`git $X`, `git "$@"`); `gh` gets only the substitution. Git aliases through `-c alias.*`, `--config-env`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` and `GIT_CONFIG_PARAMETERS` (both quote forms), also given as `NAME=value` operands of `env` or `sudo`, classify as their expansion (up to 5 levels, values split like git's `split_cmdline`; a `!` alias is shell code; an unresolvable one is level B). Docker global options, `container VERB`, `image build`, compose options and `docker-compose` classify like the short forms; short-flag clusters are read like pflag (`D`, `v`, `h` boolean, `c`, `H`, `l` take a value), an unknown option is read both ways, and more than `MAX_DOCKER_FORMS` = 8 readings is `readings_cap`.
  - Forwarding functions: `f() { "$@"; }; f docker restart x` classifies the call with its arguments substituted (one level, at most 16 calls; `$@`, `$*`, `$N`, `${@:N[:M]}`, zsh `$argv`, straight-line `shift [n]`). A call that cannot be resolved is level B `dynamic_code`: the function passed to `xargs`/`eval`/`watch`/`find -exec`, named in a nested shell string, chains of functions, more than 16 calls, an expansion landing at the program or verb position, or a positional form not modeled (`${@:$n}`, `${1:-x}`, `${!1}`, `$@[i]`, `set --`, `shift` inside `if`, a loop, `&&` or a pipeline). A bare definition passes.
  - Rebinding: a function named like a sink, data reader, foreign interpreter or SQL client drops that exemption; `hash -p`, `hash name=path`, `enable -f` and an assignment to `PATH` (or zsh `path`) make heredoc bodies and here-strings from that offset on read as code.
  - Budgets: `MAX_COMMAND_LEN` 16384 characters (`command_too_long`, checked before any parse); `MAX_LEX_CHARS` = 8 x that, shared by every parse of one analysis (code strings, bodies and values included); each text analyzed also costs `TEXT_COST` = 128 and each value combination or code variant `VARIANT_COST` = 64 of the same budget, so fan-out fails closed (`analysis_budget`) instead of running long; plus `MAX_NESTING` 32, `MAX_CODE_DEPTH` 3, `MAX_CODE_ARGS` 16, `MAX_VALUE_CANDIDATES` 16, `MAX_READINGS` 8, `MAX_DOCKER_FORMS` 8 and `MAX_HEREDOC_OPENERS` 32. The caps are pinned by tests: a legitimate command that hits one gets a precise parse rule, never a higher cap.
  - Known limits (spec `.claude/docs/features/audit-shell-lexer/spec.md`; open items in [the backlog entry](docs/backlog/refactor/2026-11-13-audit-shell-lexer.md) and its siblings under `docs/backlog/`): a group or subshell reading a pipe (`echo 'git push' | { bash; }`), `dc` `!cmd`, git config keys that run commands (`core.pager`, `core.sshCommand`, `core.fsmonitor`, `credential.helper`, `diff.external`), `hatch env:cmd`, `pixi exec`, nvim `vim.cmd("!cmd")` and `:execute` with a variable, `doas` and the other wrappers above, same-text aliases, the arithmetic evaluation of a variable's content, `git log --grep push` still asking as `git_push`, and a planted checked-hash `.pyc`.
  - Escape valve: if a rule blocks normal work before it is fixed, set `"mode": "audit"` in `agent-audit.json` (records only, nothing denied; `test_config_contract.py` flags it on purpose) or revert the change.
- `agent-metrics.py` - the report: `agent-metrics.py` (last session), `--last N`, `--session <id>`, `--since YYYY-MM-DD [--merge]`, `--run <slug>` (one `/implement` run across sessions). It lists agent calls and durations, actions by category and actor, gates run by `test-runner`, writes checked against scope, the enforcement decisions by category (with the false-positive rule for promoting a category), and every flag with examples. A `## design-director` section appears only when the session has a `design-director` call or event: calls, writes other than to a `DESIGN_SYSTEM.md` (target 0, up to 5 examples) and a reminder to check by hand, in the transcript, calls made without a prior yes from the user (the hook does not see the conversation; target 0). A legitimate command that was blocked gets a precise parse rule (test first, entry in the backlog), never a relaxed fail-closed or a raised cap; a false-negative candidate becomes input for the lexer spec. - `tests/` - the versioned `claude-hooks` suite (stdlib `unittest`, 811 tests, about 10-11 s; needs Python >= 3.13 and `git`). One test: `-I` forbids running it by dotted name (`python3 -I -m unittest test_x.Case.test_y` cannot import the suite), so use the `-I`-safe form `python3 -I -B -m unittest discover -s .claude/hooks/tests -t .claude/hooks -k <name>`. Besides the hook modules, it has `test_shell_lexer.py` (parser), `test_shell_properties.py` (property tests with fixed seeds, checked against `bash -n` and `zsh -n`, which never execute anything) and `test_command_positions.py` (command positions, wrappers, code arguments, values, receivers). The package-level `load_tests` runs every module's independent cases in one `ForkedSuite`, heavy modules first. It is hermetic: `tests/__init__.py` points `AGENT_AUDIT_DIR` at a temp dir (nothing reaches `~/.claude/metrics`) and drops `GIT_*` variables. Mechanism tests use a fixed `TEST_CONFIG`; only `test_config_contract.py` reads the live `agent-audit.json` and `settings.json`, checking floors rather than exact actions, so promoting a `warn` category to `block` does not break it. `tests/_support.py` is the shared toolkit for new tests: `audit` and `metrics` (the loaded hook modules), `TEST_CONFIG` and `config(**overrides)`, `declare_docs_root()` (writes a root `CLAUDE.md` with the `- docs root:` line), `TempRepoCase` (temporary git repo with `write_run()`, `declare()`, `make_scratchpad()`, `eval_at()` and `evaluate()`; `eval_at()` takes `scratchpad=`), `payload()` (hook JSON for `main`, a subagent or a named agent; takes `scratchpad=`), `call_main()` (runs `main()` in process and returns `HookResult(output, records)`), `HookProcess` (runs a copy of the hook as a real process, for the stdin/stdout/exit contract), `read_jsonl()` and the `assert_no_git_root()` environment check. A helper only one module needs stays in that module.


## templates/

Reference docs for how a new project should be structured, one per stack, each a `STRUCTURE.md` with the folder tree plus a "why this shape" section explaining the reasoning (so it can be adapted, not followed blindly). Used by the `new-project` skill; also readable directly.

`project-root` is the monorepo wrapper every new project gets: root-level `CLAUDE.md`/`PRD.md`/`OPEN_QUESTIONS.md`/`CONSTRAINTS.md`/`DEPLOY.md`/`DESIGN_SYSTEM.md`, a root `docker-compose.yml` (services on their `dev` Dockerfile target + infra with healthchecks) with `.env.example` and `gitignore.template`, a `docs/` folder built from `docs-structure/` (`features/<slug>/` with plan, spec and log, plus backlog - what `@planner`, `/implement` and the agents expect), a `services/` folder with one subfolder per service, and `.github/` with one workflow per service.

Templates are a contract between agents and skills: every section has a writer and a reader (the full map is in `agent-workflow.md`, section 11). The root `CLAUDE.md` carries three sections agents read - `Local runtime` (how to validate against the instance the user runs), `Test suites` (which suites `test-runner` runs per task, per run or only on demand) and `Workflow` (the docs layout). There is no `TASKS.md`: work in progress is the features Index and what comes next is the backlog. `OPEN_QUESTIONS.md` holds only project-level decisions.

`ci/` holds the GitHub Actions templates: one workflow per stack (`node.yml` for NestJS/Express/React, `react-native.yml`, `spring-maven.yml`/`spring-gradle.yml`, `go.yml`, `python.yml`, `rust.yml`), the reusable `_docker-image.yml`, and `dependabot.yml`. Each service's workflow runs only when `services/<service>/**` changes: `quality` (lint, typecheck, tests) and `build` in parallel, then `image` (Docker build, published to GHCR on pushes to `main`); mobile runs `quality` only. Every action is pinned by commit SHA and kept current by Dependabot. `ci/README.md` documents placeholders, variants (pnpm/yarn, test database) and what each service must provide.

`new-project` accepts a one-line profile, e.g. `/new-project shop backend=nestjs frontend=react infra=postgres,redis ci=full docs=pt` (services, stacks, infra, `ci=full|check|none`, docs language), asks only for what is missing, and shows the tree for confirmation before writing anything.

Each of the other templates describes the contents of one `services/<name>/` folder, not a repo root by itself: `node-nestjs-api`, `node-express-typeorm-api`, `node-express-prisma-api`, `spring-boot-api` (backend), `node-ts-react` (frontend), `react-native` (mobile), plus the generic `go`, `python`, `rust`.

Structures favor feature-first organization (folders per domain, not per technical layer), a thin wiring-only entrypoint, isolated data access, and validated config that fails fast - consistent with the global CLAUDE.md preference for robustness and long-term maintainability over short-term dev cost.

`onboarding/` holds the `BACKEND.md`/`FRONTEND.md`/`MOBILE.md`/`LUA.md` skeletons the `onboard` skill fills in when reverse-engineering an existing project (`LUA.md` is a single file at the repo root with one block per Lua unit, for Neovim plugins and configs, OpenResty gateways, embedded configs and the like, including projects with no service folders) - documents current reality, not the prescriptive shape the other templates describe.
